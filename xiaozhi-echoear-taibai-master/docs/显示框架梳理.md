# EchoEar 显示框架梳理与重构方案

> 状态：**只做分析，未改任何代码**。
> 目的：把"为什么越修越坏"讲清楚 —— 不是又有几个 bug，而是**架构上缺一层**。
> 日期：2026-10-27

---

## 一、现在到底有几套东西在抢屏幕

当前代码里，同一块 ST77916 面板（SPI2_HOST，QSPI，40MHz，trans_queue_depth=10）被**三方**同时驱动：

| 角色 | 拥有者 | 线程 | 何时跑 |
|---|---|---|---|
| **A. gfx 表情引擎** | `EmoteEngine`（emote_display.cc） | `gfx_task`，核心 0，优先级 5 | 只要 `disp.child_list != NULL` **就一直整屏重绘** |
| **B. LVGL 桌面** | `PageManager`（coze_ui） | `taskLVGL`，核心 1，优先级 1 | `lvgl_port_resume()` 之后每 1ms 醒一次 |
| **C. 触摸任务** | `touch_event_task` | `touch_task`，核心 1，优先级 5 | 有触摸事件时，**直接调用 A 和 B** |

三方共享同一个 `esp_lcd_panel_io_handle_t`，它们之间**没有任何"总线归属"协议**。

## 二、四个结构性缺陷（这才是"越改越坏"的原因）

### 缺陷 1：`esp_lcd_panel_draw_bitmap` 不是原子的 —— 这是所有花屏/报错的真凶

看驱动源码 `esp_lcd_st77916.c:472-501`：

```c
tx_param(io, LCD_CMD_CASET, ...);   // ① 命令，同步轮询，占用总线
tx_param(io, LCD_CMD_RASET, ...);   // ② 命令，同步轮询，占用总线
tx_color(io, LCD_CMD_RAMWR, ...);   // ③ 像素数据，异步排队（queue_trans）
```

**一次 `draw_bitmap` = 两次同步轮询 + 一次异步排队。** 中间可以被打断。

于是您看到的这组错误就能完整解释：

```
E spi_master: spi_device_acquire_bus(1357): Cannot acquire bus when a polling transaction is in progress.
E lcd_panel.io.spi: panel_io_spi_tx_param(213): acquire spi bus failed
E st77916: panel_st77916_draw_bitmap(484): send command failed
```

第 484 行正是 **CASET**（①）。含义：**A 正在发像素（③，异步排队、总线被占），B 此时插进来想发 CASET（①，需要轮询拿总线）→ 拿不到 → 整帧丢弃。**

更糟的是 `trans_queue_depth = 10`：A 的像素数据可以排 10 个在队列里，**B 完全看不见这些排队项**。所以"抢总线"这件事在当前设计下**根本防不住**，加锁也防不住（A 排完队就返回了，锁早就放了）。

> **任何人肉判断"表情静默了就没事"都是错的**，因为 gfx 只要还有对象就会每轮刷。

### 缺陷 2：`SetDesktopActive` 是"门帘"，不是"开关"

我在 `emote_display.cc` 里加的是**入口拦截**：

```cpp
if (g_desktop_active) { return; }   // SetEmotion / SetStatus / UpdateStatusBar ...
```

但它拦不住**已经在跑的东西**：

- `gfx_task` 只要 `child_list != NULL` 就继续 `gfx_refr_handler()` 整屏重绘；
- `gfx_timer_handler` 里的动画定时器继续推进帧；
- 我后来补的 `gfx_anim_stop()` 只停了两个动画对象，**没停刷新循环本身**。

所以 LVGL 刷一帧 → gfx 立刻盖回去 → LVGL 再刷…… 交替写入同一个面板。这就是"左滑闪现时钟"和"自顶向下刷新"的来源。

**结论：需要在"引擎层"真正停止 gfx 刷新，而不是在 API 层拦截。**

### 缺陷 3：锁关系是交叉的 —— 死锁与优先级反转都埋着

现在的锁：

```
gfx 锁  : gfx_emote_lock(handle)        递归互斥量
LVGL 锁 : lvgl_port_lock()              xSemaphoreCreateRecursiveMutex
PageManager::mutex_                     普通互斥量
```

调用方：

- `touch_task`（优先级 5，核心 1）→ 取 PageManager::mutex_ → 取 LVGL 锁
- `taskLVGL`（优先级 1，核心 1）→ 取 LVGL 锁 → 在 flush_cb 里 **调 `esp_lcd_panel_draw_bitmap`**（占 SPI）
- `gfx_task`（优先级 5，核心 0）→ 取 gfx 锁 → **调 `esp_lcd_panel_draw_bitmap`**（占 SPI）

**两个不同核心、两把不同的锁，却抢同一根 SPI 总线 → 互斥根本没有覆盖到。**

我上轮把 `HandleSwipe` 改成 `lvgl_port_lock(0)` 只是把"阻塞 1 秒饿死音频"暂时压住了，**没有解决交叉**：`taskLVGL` 拿不到 SPI 时会在 `draw_bitmap` 里反复重试，而 `taskLVGL` 优先级只有 1，它一旦在自旋，**核心 1 上的触摸任务和音频任务全都被拖住** —— 这就是"表情卡死、串口有 shake 但脸不动"。

### 缺陷 4：状态机是空的

现在"当前在哪一页"这件事，实际上是**散落在 6 个地方**的布尔量：

| 变量 | 位置 | 含义 |
|---|---|---|
| `g_desktop_active` | emote_display.cc（文件级 static） | 表情是否静音 |
| `in_lvgl_` | PageManager | 是否在 LVGL 模式 |
| `current_` | PageManager | 当前页指针 |
| `lvgl_ticking_` | PageManager | LVGL tick 是否在跑 |
| `g_flush_owner` | emote_display.cc（原子量） | 这帧是谁发的 |
| `g_flush_last_block_` | emote_display.cc | gfx 帧内第几块 |

**6 个变量描述 1 个状态**，任何一处漏更新就永久错位。这就是为什么"改好一处、坏另一处"。

## 三、正确的框架应该长什么样

核心思想只有一句：**屏幕只有一个主人，任何时刻只有一个后端能碰 SPI。**

```
                    ┌──────────────────────────────┐
                    │      DisplayManager          │  ← 唯一的状态机
                    │  (单一线程独占，见下)          │
                    └───────────┬──────────────────┘
                                │  只在状态切换时才动
              ┌─────────────────┼─────────────────┐
              │                 │                 │
        ┌─────▼─────┐     ┌─────▼─────┐     ┌─────▼─────┐
        │ GfxBackend│     │LvglBackend│     │ (将来)    │
        │  表情页    │     │  桌面/App  │     │ 新页面     │
        └─────┬─────┘     └─────┬─────┘     └───────────┘
              │                 │
              └────────┬────────┘
                       │  严格的交接协议
              ┌────────▼─────────┐
              │   Panel 单写者    │  ← 只有它能调 draw_bitmap
              └──────────────────┘
```

### 3.1 后端必须具备 `Suspend()/Resume()`（现有代码没有）

这是最关键的缺失。现在的"切换"是：

```cpp
// 伪代码，说明现状
gfx_mute_(ctx, true);      // ❌ 只是拦 API，gfx_task 还在刷
lvgl_port_resume();        // ❌ 没说等 gfx 停下来
```

必须改成**同步、可确认的交接**：

```cpp
// 伪代码，说明目标
bool GfxBackend::Suspend() {
    lock_gfx();                       // 挡住新帧
    ctx->disp.suspended = true;       // 告诉 gfx_task：别刷了
    wait_until_gfx_idle();            // 等当前这一帧彻底发完（含队列）
    unlock_gfx();
    return true;
}
```

**"等当前帧彻底发完"是必须的**，因为 `trans_queue_depth = 10`，队列里可能还压着像素。判断依据：最后一次 `on_color_trans_done` 回调 + `esp_lcd_panel_io_spi` 的 `wait_trans_finish`。

### 3.2 交接必须是"先停后起"，不能交叠

```
切到桌面：  gfx.Suspend()  ──确认完成──▶  lvgl.Resume()
切回表情：  lvgl.Suspend() ──确认完成──▶  gfx.Resume()
```

中间**任何一步失败都要回滚**，不能"尽力而为"。

### 3.3 触摸只走一条路

现在触摸有两条路（`FeedTouch` 喂 LVGL、`HandleSwipe` 切页），且在两个不同线程语义里。应该统一成：

```
touch_task ──▶ DisplayManager::OnTouchEvent(type, x, y)
                     │
                     ├─ 是滑动？→ 交给状态机决定切页
                     └─ 是点击？→ 交给当前后端
```

状态机是**唯一**决定"这一下触摸意味着什么"的地方。

### 3.4 唯一的"当前状态"变量

```cpp
enum class ScreenState {
    EMOTE,          // gfx 表情页（默认）
    DESKTOP,        // LVGL 桌面
    APP,            // LVGL 某个 App 内
};
```

一个 `ScreenState`，一个 `suspended_backend`，总共两个变量。其余全部是它的纯函数。

## 四、现在这个 Flush 分发器正确吗？

**部分正确，但治标不治本。**

`emote_display.cc` 里的 `OnFlushIoReady` 分发器：

```cpp
if (g_flush_owner.load() == kFlushOwnerLvgl) {
    done();          // 交给 LVGL
    return true;
}
gfx_emote_flush_ready(handle, g_flush_last_block_);
```

这一层解决的是「**完成回调该通知谁**」，确实必要（否则 gfx 会提前复用还被 DMA 读取的缓冲 → 折叠）。

但它解决不了「**传输该由谁发起**」。**发起方冲突才是现在的问题**，`g_flush_owner` 只在回调时才知道结果，已经晚了。

## 五、`g_desktop_active` 静音的效果评估

| 调用 | 是否被拦住 | 说明 |
|---|---|---|
| `SetEmotion` | ✅ | 存了 `g_last_emotion` 就直接 return |
| `SetStatus` | ✅ | 直接 return |
| `UpdateStatusBar` | ✅ | 每秒的 UI 更新被挡 |
| `gfx_anim_start` 动画 | ❌ | **gfx_task 自己在跑** |
| `gfx_refr_handler` 整屏重绘 | ❌ | **没停** |
| 队列里残留的像素 | ❌ | **没清** |

所以"表情已静默"这个判断是**不成立**的。这也是您看到的"有 shake 但脸不变"的直接原因：**脸其实在变，只是被 LVGL 盖住了、或者两方互相覆盖。**

## 六、建议的重构方案

### 方案一：最小可用（推荐先做这个）

**不动现有架构，只补上"真正停住"的能力。**

1. 给 `gfx` 加一个 `gfx_emote_set_suspended(handle, bool)` 外部开关

   **已确认：gfx 组件完全没有暂停接口。** `gfx_core.h` 的公开 API 只有：
   `gfx_emote_init` / `deinit` / `flush_ready` / `get_user_data` / `get_screen_size` /
   `lock` / `unlock` / `set_bg_color` / `is_flushing_last`。
   **没有任何 suspend / pause / stop / enable 接口。**

   所以必须改组件内部（`gfx_core.c:279`）：

   ```c
   if (ctx->disp.child_list != NULL && !ctx->disp.suspended) {
       gfx_refr_handler(ctx);
   }
   ```

   这是一个 `managed_components/` 下的第三方组件，**改动会被 `idf.py` 的依赖校验覆盖**。
   处理办法（三选一，需您定夺）：
   - **(a) 推荐**：把 `managed_components/espressif2022__esp_emote_gfx` 复制到 `components/esp_emote_gfx`（本地组件优先于托管组件），然后在 `main/idf_component.yml` 里那行加 `override_path` 或直接删掉托管依赖。本地 `components/` 目录天然优先，改动不会被依赖管理器覆盖。
   - (b) 不改正组件，改用 `gfx_emote_lock()` 长时间持锁 —— **不推荐**，会饿死其他调用。
   - (c) 用 `gfx_obj` 的可见性全部隐藏来间接停刷 —— **不可靠**，`child_list` 非空仍会刷。

   > 现状：`main/idf_component.yml` 声明 `espressif2022/esp_emote_gfx: ^1.1.2`，
   > 版本范围是宽松的 `^`，直接改 `managed_components/` 里的代码会在下次 `idf.py reconfigure` 时被覆盖。
2. 给 `esp_lcd_panel_io_spi` 加一个 `wait_all_pending(io)` 辅助函数（用 `esp_lcd_panel_io_spi` 的客户完成回调计数）
3. `SetDesktopActive(true)` 改成：停动画 → 置 `suspended` → 等队列空 → 确认返回
4. `SetDesktopActive(false)` 改成：先 `lvgl_port_stop()` → 确认 → 再清 `suspended` → 重启动画

**优点**：改动集中，风险可控，能立刻验证"三个后端打得动打不动"。
**缺点**：本质还是"两个后端在同一根 SPI 上分时"，**没有根本上消除总线争用**。

### 方案二：单写者层（正确做法，但改动大）

增加一个 `PanelWriter`，它是**唯一**调用 `esp_lcd_panel_draw_bitmap` 的地方。gfx 和 LVGL 都只往它提交"我要刷这块区域 + 数据指针"，由它串行化。

**优点**：从结构上根除总线争用，以后加第三个后端也不会重蹈覆辙。
**缺点**：需要改 gfx 组件（或做一层适配），并重写 LVGL 的 flush_cb，工作量大约是方案一的 3 倍。

### 方案三：彻底切换（最干净，但要重写表情页）

放弃"gfx 和 LVGL 共存"，全部迁到 LVGL，用 LVGL 的矢量动画重做表情。

**优点**：只有一个渲染后端，问题彻底消失。
**缺点**：表情动画质量可能不如 gfx（gfx 是专门做表情的），工作量大。

---

## 七、我的建议

**先做方案一，并且立刻用"是否还有 SPI 报错"作为唯一验收标准。**

理由：
- 您现在的痛点是"报错 + 卡死"，方案一有针对性地解决；
- 方案一做完后，如果 SPI 报错消失、桌面能稳定显示、切回表情正常 —— 那就说明"分时"够了，不必付出方案二/三的代价；
- 如果方案一做完了报错**还在**，那就证明"分时"在 ESP32-S3 上不成立，**这时才值得做方案二**。

**不要现在继续在 `page_manager.cc` 里打补丁了**，那确实是在错误的层次上修。

## 八、需要您确认的几件事

1. **是否接受方案一作为下一步？** 还是希望直接上方案二（单写者层）？

## 附：本轮确认的事实清单（供核对）

- `esp_lcd_st77916.c:472-501`：`draw_bitmap` = 2 次同步 `tx_param` + 1 次异步 `tx_color`，非原子。
- `esp_lcd_st77916.h:96-110`：`trans_queue_depth = 10`，`pclk_hz = 40MHz`，QSPI quad_mode。
- `gfx_core.c:279-281`：`if (ctx->disp.child_list != NULL) gfx_refr_handler(ctx);` —— **只要还有对象就每轮整屏重绘**。
- `gfx_core.c:637-707`：`gfx_refr_handler` 按块切帧、逐块 `draw_bitmap` + `xEventGroupWaitBits(50ms)`。
- `esp_lvgl_port.c:216-247`：`taskLVGL` 循环，`lv_timer_handler()` 返回值决定 `task_delay_ms`；**优先级 1**。
- `EchoEar.cc:1424`：`touch_task` 优先级 5，栈 4KB，核心 1。
- `EchoEar.cc:1267-1276`：LVGL 模式下先 `FeedTouch` 喂坐标，再由 `HandleSwipe` 切页 —— 两条路径。
- `EchoEar.cc:1449-1522`：面板初始化顺序 = SPI bus → panel_io → panel → EmoteDisplay → PageManager → 背光。
